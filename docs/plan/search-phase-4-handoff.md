## Big indexes (asked by the PI migration, PR #58)

The PI migration left its 112 problem statements out of the index to stay
under 300 KB. That number was only the **stop threshold of decision 8 for
S0** (to re-plan if EDados came out too big); the kit has no size limit, and
`uc-site.py` only warns above `LARGE_INDEX` = 500 KB. Measured on EDados
(main after S4): 294 KB raw, **74 KB gzipped**.

Options evaluated in S4:

| Option | Gain | Cost |
| --- | --- | --- |
| Fragmented / per-folder index loaded lazily | none for search: every query needs every text, so all shards load on the first query anyway | new format `v: 2`, script and loader changes |
| Compaction: drop from `w` the words already in the title, excerpts at 100 characters | −12 % (EDados 294 → 259 KB, 74 → 65 KB gzipped) | small change in `uc-site.py`, same format |
| Keep one file, raise the warning | — | none |

**Recommendation for S5:** put the statements back in the PI index; raise
`LARGE_INDEX` to 1 MB (≈ 250 KB gzipped, downloaded once, only when the
search opens, then cached) and say in `manter.html` that a bigger index only
makes the first search slower; add the compaction if it is cheap. Note: if
the DCC Apache does not gzip `.js`, the download is the raw size; `publicar.html`
could show the `.htaccess` lines (`AddOutputFilterByType DEFLATE
text/javascript application/javascript`) as an optional step. Revisit
sharding only if a site passes ~2 MB.
