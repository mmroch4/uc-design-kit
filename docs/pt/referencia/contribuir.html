Referência

Contribuir

Para quem mantém o kit ou quer propor uma alteração: como o repositório está organizado, como construir e testar, como documentar e como lançar uma versão. O texto de referência é o CONTRIBUTING.md, em inglês.

Princípios

  1. Nada a instalar para quem usa. Um professor usa o kit com duas linhas no <head>. As ferramentas (testes, minificação) são só para quem mantém.
  2. O contrato primeiro. O docs/api.md define componentes, atributos, campos, tokens, classes e a API JavaScript. Muda-se num pull request próprio, antes do código que depende dele.
  3. Um componente, um ficheiro. kit/src/components/uc-<nome>.js, kit/src/css/components/uc-<nome>.css e uma página de teste em tests/pages/ com todos os estados.
  4. Light DOM e scripts clássicos, para o CSS da página se aplicar e tudo funcionar a partir de file://.
  5. Acessível por omissão: WCAG 2.1 AA, teclado, foco visível, alvos de 44 px, nada transmitido só pela cor.
  6. Nunca partir uma versão publicada. Ver Versões.

O repositório

Pastas do repositório
PastaConteúdo
kit/src/O código do kit: core/, components/, css/, i18n/. A ordem de junção está em manifest.json.
kit/v1/O kit construído (minificado, com source maps). Gerado, mas guardado no repositório: o site não tem passo de compilação.
docs/O contrato (api.md) e esta documentação: pt/, demos/, assets/, nav.json.
examples/, template/O site real de Estruturas de Dados e o modelo inicial.
tests/pages/Uma página por componente com todos os estados.
scripts/Construção, verificações e lançamentos.

Construir e testar

npm ci                          # Playwright, axe-core and esbuild (maintainers only)
npm run build                   # kit/v1, generated docs parts, search index, template zip
npm test                        # check-docs --strict, then check-pages
npm test -- uc-week             # only the pages whose path contains "uc-week"
npm run test:update-screenshots # also writes tests/screenshots/*.png
npm run test:dom -- --update    # rewrites tests/dom-record.json (a change meant to alter pages)
Verificações automáticas
VerificaçãoO que confirma
build:checkO kit, as partes geradas da documentação, o índice de pesquisa e o zip do modelo correspondem às fontes; nenhuma versão congelada foi alterada.
check-docsNavegação, títulos, links e âncoras; e cobertura: cada componente, atributo, campo do course.js, bloco, token, membro e evento da API, runner incluído e classe que o kit gera está na página certa.
check-pagesEm cada página (testes, exemplos, modelo, documentação e demonstrações): sem erros na consola por HTTP e em file://, sem ficheiros em falta, sem deslocamento horizontal a 360 px, sem violações graves do axe (WCAG 2.1 AA), conteúdo visível sem JavaScript.
check-domNada mudou sem querer: o DOM depois de o kit o construir e a árvore de acessibilidade de cada página são iguais aos de tests/dom-record.json, e nenhum ficheiro de kit/v1/ ou widgets/v1/ ficou maior (gzip). Uma refatoração passa sem tocar no registo; uma alteração que muda páginas atualiza-o (--update) no mesmo pull request. --against=origin/main mostra as diferenças.

As páginas são verificadas com a data fixa de 27 de novembro de 2025 (TEST_TODAY muda-a). O GitHub Actions corre build:check e as verificações de npm test em cada pull request, divididas em 4 tarefas paralelas (--shard=i/4), cada uma a abrir várias páginas ao mesmo tempo (--concurrency=n); o estado obrigatório check só fica verde quando as quatro passam. As capturas de ecrã só se tiram em main. O Cloudflare Pages publica uma pré-visualização.

Documentar uma alteração

A documentação é HTML escrito à mão, com partes geradas entre marcadores <!-- docs:… --> (cabeçalho, barra lateral, "Nesta página", anterior/seguinte, demonstrações e tabelas de classes) que o npm run build preenche. Nunca se edita dentro desses marcadores.

Um componente novo

  1. Acrescentar o componente e os atributos ao docs/api.md, secção 3.
  2. Copiar docs/pt/componentes/uc-week.html para uc-<nome>.html e seguir o mesmo modelo: demonstração, utilização, exemplos, atributos, configuração, personalizar, acessibilidade, sem JavaScript, ver também.
  3. Criar as demonstrações em docs/demos/uc-<nome>/, com o código marcado entre <!-- demo:start --> e <!-- demo:end -->, e usá-las com <!-- docs:demo src="…" title="…" height="…" -->.
  4. Acrescentar a página ao docs/nav.json (com "component"), à visão geral dos componentes, e um bloco docs:classes em Classes CSS estáveis.
  5. npm run build e npm test. O check-docs falha enquanto faltar a página, um atributo ou uma classe.

Um widget novo

Os widgets de algoritmos (widgets/src/<nome>/) têm a sua própria lista: algoritmo puro testado contra uma referência, frases em português e em inglês, página e duas demonstrações, no máximo 8 KB. Está em Criar um widget e em widgets/template/README.md.

Outras alterações

  • Um atributo, campo do course.js, token ou membro da API novo: primeiro no api.md, depois na tabela da página correspondente. O teste diz qual.
  • Uma classe nova gerada pelo kit: na tabela "Personalizar" do componente se for estável, senão na lista Internas.
  • Uma página nova: copiar uma página do mesmo grupo e acrescentá-la ao nav.json. Entra sozinha na pesquisa.
  • As convenções de escrita (português europeu, ids sem acentos, links com index.html explícito) estão no CONTRIBUTING.md, em Writing conventions, com os passos para acrescentar um exemplo real.

Pull requests

  • Código, identificadores, comentários e mensagens de commit em inglês.
  • Uma linha no CHANGELOG.md, em Unreleased.
  • npm test verde antes de abrir o pull request; capturas do antes e depois quando o aspeto muda.

Lançar uma versão

  1. Mudar a versão em package.json, a única fonte: o npm run build escreve-a em kit/src/core/namespace.js (UC.version), widgets/src/core/version.js e template/uc-site.py, e o build:check falha se divergirem. Passar as notas de Unreleased para a nova versão no CHANGELOG.md.
  2. npm run build e depois npm run snapshot, que copia kit/v1/ para kit/vX.Y.Z/ e escreve o seu SHA256SUMS.
  3. Fundir em main (publicado automaticamente) e criar a etiqueta vX.Y.Z.
  4. Voltar a pôr a versão seguinte com -dev.

Lançar uma versão dos widgets

Os widgets (widgets/v1/) têm a versão do kit (vem do package.json) e saem com a mesma etiqueta vX.Y.Z. KIT_MIN, em widgets/src/core/version.js, é a versão mais antiga do kit com que funcionam.

  1. Todos os meta.json com "status": "stable" (o snapshot recusa-se sem isso). Passar as notas de Widgets para ## Widgets [X.Y.Z] no CHANGELOG.md.
  2. npm run build e depois npm run snapshot:widgets, que copia widgets/v1/ para widgets/vX.Y.Z/ e escreve o seu SHA256SUMS.
  3. Fundir em main com a etiqueta vX.Y.Z do kit. A partir daí, a verificação abre tests/widgets/compat.html com widgets/v1/ e com cada versão congelada.

Os pormenores de publicação (cabeçalhos de cache, domínio, espelho no jsDelivr) estão em docs/deployment.md.
