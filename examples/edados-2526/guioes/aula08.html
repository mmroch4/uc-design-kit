Exercício 2) Complexidade do TAD Conjunto

Para a implementação ArrayListIntSet (que usava um array como lista dos números do conjunto), qual é a complexidade temporal de cada um dos seguintes métodos? (usa a notação Θ)

  1. contains(int x)
  2. add(int x)
  3. remove(int x)
  4. size()
  5. clear()
Soluções
  • contains(int x): Θ(n), é preciso percorrer a lista de elementos.
  • add(int x): Θ(n); acrescentar em si é Θ(1), mas antes chama-se o contains, que custa Θ(n).
  • remove(int x): Θ(n), é preciso percorrer a lista de elementos.
  • size(): Θ(1), basta devolver o conteúdo de uma variável.
  • clear(): Θ(1), basta modificar o conteúdo de uma variável.

Na aula 5 foi sugerida uma implementação usando um array de booleanos (em vez de manter uma lista de números). Recordando o essencial: manter um array isElem[] de valores booleanos; isElem[i] diz se o número i está ou não no conjunto; o tamanho do array determina o maior número possível; uma outra variável size guarda o número de elementos. Por exemplo, o conjunto {1, 5, 7} seria representado por isElem[] = {F,T,F,F,F,T,F,T,F,F} e size = 3:

Array isElem para o conjunto {1, 5, 7}
Índice0123456789
isElemFTFFFTFTFF

Para esta implementação, qual é a complexidade temporal de cada um dos mesmos 5 métodos do TAD IntSet? O que melhorou em relação ao ArrayListIntSet? Qual é o tradeoff? (Ou seja, para ter melhor complexidade temporal, de que passamos a precisar em termos de memória? Quais são as limitações desta nova implementação?)

Soluções
  • contains(int x): Θ(1), basta devolver uma posição do array.
  • add(int x): Θ(1), basta marcar uma posição do array a true.
  • remove(int x): Θ(1), basta marcar uma posição do array a false.
  • size(): Θ(1), assumindo que a quantidade de elementos está guardada num atributo.
  • clear(): Θ(k), é preciso percorrer todo o array até ao valor máximo k.

No essencial melhorámos a complexidade do contains, do add e do remove, e só piorámos a do clear. O tradeoff é que passamos a precisar de mais memória, Θ(k) contra Θ(n), onde k é o maior elemento possível de armazenar. Por isso estamos limitados a elementos cuja magnitude caiba na memória (por exemplo, guardar dois long seria fácil num ArrayList, mas num array de booleanos implicaria ter espaço para 263 − 1 elementos, o que não é de todo possível num computador atual). Além disso, só podemos guardar coisas indexáveis (por exemplo, seria fácil guardar um conjunto de String num ArrayList, mas num array de booleanos teríamos de ter uma maneira de converter String em posições inteiras).

Exercício 3) Previsão do tempo de execução

Imagina que tens um programa P que recebe como input n números. Ao executá-lo com testes aleatórios, obtiveste os seguintes tempos de execução:

  • com n = 300 demorou 1,5 segundos;
  • com n = 600 demorou 12,0 segundos;
  • com n = 1200 demorou 1 min 36 s.

Qual é a complexidade temporal mais provável do programa P? Justifica.

Solução

Quando o tamanho do input duplica, o tempo aumenta 8 vezes (12 s / 1,5 s = 96 s / 12 s = 8). Por isso a complexidade parece ser O(n3), pois (2n)3 / n3 = 8.

Dá uma estimativa de quanto tempo demoraria o programa num caso com 5000 números. Justifica.

Solução

Seja f(n) = n3 e consideremos n1 = 300 e t1 = 1,5. Sabendo que n2 = 5000, queremos estimar t2:

t2 = f(n2) / f(n1) × t1 = 50003 / 3003 × 1,5 ≈ 6944 s ≈ 115 min

Uma solução quadrática ainda não chega: temos de a melhorar para tempo linear. Para isso vamos usar o algoritmo de Kadane.

Considera que best(i) representa o melhor subarray que termina na posição i. Como "caso base", sabemos que best(0) = v[0] (é o único subarray possível que termina na primeira posição).

Se soubermos o valor de best(i), como calcular o valor de best(i+1)?

  • Se best(i) for positivo, então best(i+1) = best(i) + v[i+1]: como os subarrays têm de ser contíguos, se aproveitarmos algo "de trás", terá de ser o melhor possível a terminar na posição anterior. Por exemplo, para o array [4, −2, 1, 5]:
    best(i) para o array [4, −2, 1, 5]
    i0123
    v[i]4−215
    best(i)4238

    best(2) = 3, obtido com o subarray [4, −2, 1]. best(3) = best(2) + v[3] = 3 + 5 = 8, obtido com o subarray [4, −2, 1, 5] (estendeu-se o subarray anterior).

  • Se best(i) for negativo, então best(i+1) = v[i+1], pois o que está "para trás" só pode fazer diminuir a soma do subarray a terminar na posição i+1. Por exemplo, para o array [−5, 2, −3, 4]:
    best(i) para o array [−5, 2, −3, 4]
    i0123
    v[i]−52−34
    best(i)−52−14

    best(2) = −1, obtido com o subarray [2, −3]. best(3) = v[3] = 4, obtido com o subarray [4] (não se estendeu o subarray anterior).

No fim, o melhor subarray é o maior valor de best(i) para qualquer i (o melhor pode terminar em qualquer posição).

Para calcular isto basta percorrer o array v[] uma única vez e, em cada iteração, calcular em tempo constante a melhor soma a terminar na posição atual a partir da melhor soma a terminar na posição anterior. A complexidade temporal fica, portanto, linear.

Implementa esta solução e submete-a, verificando que já passa todos os testes sem exceder o tempo limite.

Exercícios extra para consolidação de conhecimentos

Tens mais dois pequenos problemas nesta aula em que a solução mais "bruta" em termos de complexidade temporal não passa no tempo e tens de fazer algo um pouco mais eficiente.

Problema [ED222] Salvando os Ruivacos, no Mooshak. Uma solução "bruta" que tente todos os intervalos e, para cada um, percorra todos os seus elementos para ver quantos são maiores ou iguais a T pode demorar Θ(N2) (basta imaginar o caso em que K = N/2: temos N/2 + 1 intervalos, cada um com tamanho N/2, para verificar). Isto não chega para passar no tempo e precisamos de uma solução melhor…

Dicas
  • Imagina que já processaste o intervalo [a, b] (entre as posições a e b) e obtiveste Qa, a quantidade de elementos maiores ou iguais a T nesse intervalo.
  • O próximo intervalo a considerar é [a+1, b+1]. O que muda? Apenas desaparece a posição a e entra a posição b+1. O novo valor Qa+1 é igual a Qa, menos 1 se o valor da posição a for ≥ T, mais 1 se o valor da posição b+1 for ≥ T.
  • Para cada novo intervalo precisamos apenas de um número constante de operações (considerar o elemento que sai e o elemento que entra). Em termos de eficiência, isto corresponde a um ciclo inicial para o primeiro intervalo, de tamanho K, e depois a percorrer os restantes N − K intervalos, gastando tempo constante em cada um. Outra maneira de pensar no mesmo algoritmo é ver que cada elemento é acrescentado uma vez ao intervalo atual e retirado uma vez. É, portanto, uma solução Θ(N) que passa em todos os casos e dá os 100 pontos.
  • Esta ideia de reutilizar o resultado do intervalo anterior para calcular mais depressa o intervalo atual chama-se sliding window, porque fazemos "deslizar" a janela corrente ao longo do input.

Problema [ED199] Tesouros de Kilmia, no Mooshak. Uma solução "bruta" que simule todas as instruções pode demorar Θ(I × N), pois cada uma das I instruções pode obrigar a percorrer N posições no pior caso. Isto não chega para passar no tempo e precisamos de uma solução melhor…

Dicas

É preciso pensar um pouco sobre o que acontece no problema e fazer uma observação importante: o Daniel cobre sempre um intervalo contíguo de posições. Se a posição mais à direita a que o Daniel chegou foi pd, então ele passou por todas as posições de B a pd, pois nunca "salta" posições. Do mesmo modo, se a posição mais à esquerda a que chegou foi pe, então passou por todas as posições de pe a B.

Assim, sabendo pe e pd, basta um ciclo que percorra todas as posições entre pe e pd e conte quantos tesouros há nesse intervalo. Para calcular pe e pd, basta calcular a posição depois de cada instrução e guardar a menor e a maior, respetivamente.

Em termos de eficiência, isto corresponde a um ciclo que processa todas as instruções e calcula pe e pd, e a um segundo ciclo que verifica as arcas entre pe e pd, ou seja, I + N operações. É, portanto, uma solução Θ(I + N) que passa em todos os casos e dá os 100 pontos.
